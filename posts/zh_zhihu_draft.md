# 知乎稿

## 标题

16GB 显存的家用电脑，怎么跑 176B 参数的稀疏 MoE：从 6.5 到 18.8 tok/s，我在 262K 上下文上踩的坑

## 正文

先说结论：一台普通 Windows 台式机——RTX 4080 SUPER 16GB、i9-14900KF、96GB DDR5——现在可以以 18.8 tok/s 的速度日常使用 Qwen3.8-Flash-Next（176.94B 总参数，IQ4_XS 量化 GGUF），上下文拉到 262K 时仍有 5.8 tok/s。补丁、基准测试程序和每个数字背后的原始日志都开源在 https://github.com/zhaoyilun/moe-working-set-16gb ，下面把整个过程和踩过的坑讲一遍。

### 问题的本质不是"把模型放进哪张卡"

176B 的模型塞不进 16GB 显存，这是显然的。但稀疏 MoE 有个特性：每个 token 实际只激活少量专家。所以真正的问题不是"怎么把整个模型搬进显存"，而是把系统分成两层：

- 96GB 内存保存完整的专家容量——负责"都有"；
- 16GB 显存保存非专家的 GPU 核心部分，加上一个常驻的热点专家工作集——负责"现在快"。

路由器选中的专家如果在显存池里，就走 GPU；不在，就走 CPU 上的原生专家路径。这和操作系统的虚拟内存是同一个思想，容量层和速度层分离。

### 三个阶段，每一步都是实测

最开始我用最粗糙的方式：`-ngl 10`，把前 10 层整个扔给 CPU。结果 6.538 tok/s，基本不可用。问题在于整层卸载把 attention、norm、router 这些明明适合 GPU 的算子也一起带回了 CPU。

第二步做结构感知的放置：只把 routed expert 权重留在内存，其余算子全部上 GPU。Decode 直接进入 15–16 tok/s 区间。

第三步在显存里建固定专家池。16K 上下文、三轮 500 token 实测：4 GiB 池 16.096，6 GiB 池 17.275，8 GiB 池 18.753 tok/s，比同路径的原生 CPU 基线高 23.91%。短上下文更好：2K 下 19.5，8K 下 18.3 tok/s。

中间有个意外发现：同一份 8 GiB 配置，CUDA Graph 开和关是 18.753 对 13.567 tok/s。也就是说"保留图复用"和"提高专家命中率"同样重要——这是后面所有设计取舍的前提。

### 追求命中率，反而更慢了

这是整个研究里我最想分享的教训。我做过一个动态调度实验：观察相邻 token 的路由，预测性地把即将用到的专家提前搬进显存。命中率从 31% 提到了 62%，听起来很美——吞吐却掉到了 11–12.8 tok/s。

原因：每个 token 多了一条控制链——读回路由、同步 CPU、做替换决策、分片搬运 gate/up/down 权重、更新映射。这条链破坏了 CUDA Graph 和流水线，把命中率赚的全赔回去了。

**缓存优化看的是端到端服务时间，不是单独命中率。** 这句话适用于很多系统设计场景。

### 262K 上下文，和 Windows 上最阴险的一个坑

上下文拉长之后，KV cache 和专家池开始抢同一块显存。KV 每上一个台阶（128K→192K→262K）要多占 0.8–1.0 GiB，池子必须让位。实测下来 q8_0-K/q4_0-V 的混合 KV 量化加 4 GiB 池，在 262K 下还有 5.776 tok/s（p50 延迟 170.7 ms），检索测试 5/5 全对，恢复一个 262K 会话只要约 14 秒。

实事求是地说：专家池的增益随上下文增长在缩水——16K 时 +23.9%，262K 时只有约 +4.6%，因为注意力/KV 的时间开始主导每个 token 的开销。长上下文更多是 KV 问题，不是专家问题。

然后是我踩过最疼的坑。q8-q4 KV 配 6 GiB 池在 262K 下"理论上放得下"，有一次短跑实测 5.5 tok/s、余量 637 MiB，看起来一切正常。但换一次 250 token 的长跑，直接崩到 0.71 tok/s，p95 延迟 7.5 秒——总需求越过物理显存后，Windows 的 WDDM 开始走共享内存分页，性能直接毁灭。最阴险的是这件事**不确定发生**：同一份配置，跑不崩取决于当时的内存驻留状态。静态算着放得下、余量小于 1 GiB 的配置，就是俄罗斯轮盘赌。

所以我现在的硬规则是：分配器余量至少留 1 GiB，池子按上下文阶梯下调——128K 以内 8 GiB，192K 用 6 GiB，262K 用 4 GiB。这条规则和那个崩溃样本的完整日志都在仓库里。

### Prefill：目前的短板和正在做的事

Decode 已经舒服了，Prefill 是下一个战场。把物理 ubatch 从 2K 提到 8K，同一 16K prompt 的吞吐从 287 提到 524 tok/s（三轮均值），32K 单轮 617。但 262K 的冷预填充还要 786.9 秒——这是系统里最大的单次等待。我正在做专家分桶加 grouped GEMM 的预填充路径，目标是冲过 1000 tok/s，第一版还没落地，数字出来会更新到仓库。
